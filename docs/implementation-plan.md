# Team Memory v0.1 开发与验收计划

首个客户端是 **Codex**。选一个真实合作项目，在全新会话中验证三件事：能否找回用户已确认的偏好，能否回答项目当前决定及其依据，能否认出一条尚待当事人确认的分工。CoPaw 提供实现参考，整套实验可在 Friday 离线时完成。**第一版群聊记忆仅支持飞书**，其接入单独验收。

## 1. 第一条要跑通的业务用例

用虚构项目 `atlas` 编写固定样例，随后用同一组问题验证真实项目。

| 输入，按时间顺序 | 应产生的结果 |
| --- | --- |
| 周一，用户在 Codex 明确说“以后给我方案时，先列待决定的事项” | 在该用户的个人空间记录偏好。换一个项目仍可取用，其他项目成员看不到。 |
| 用户又说“我猜小林会负责验收，会上有人建议周五上线” | 保留原话及出处。“小林负责验收”和“周五上线”都缺少确认。用户可以在自己的待复验列表看到，项目当前决定里没有这两项。 |
| 周二，项目负责人在共享评审记录中确认“上线定在下周一”，小林在同一记录中接受验收任务 | 产生两条有各自证据的项目记忆。项目成员能看到决定和分工。原来那条个人观察仍然私有。 |
| 周三，负责人把上线时间改到周二 | 系统关联旧决定，呈现变更原因和依据。有冲突时保留原有效版本，复验通过后再切换。历史查询仍可还原周二时的决定。 |

将样例中的相对日期与事件时间同时保存。测试固定时区和日期，断言具体年月日，避免“下周一”随查询当天漂移。

## 2. 服务边界与技术选择

- **接入层**使用 Python、FastAPI 和 MCP Python SDK。HTTP 与 Streamable HTTP MCP 调用同一组应用函数。Codex 配一个服务地址和 Agent 凭证即可使用。其他 Agent 可以只用 HTTP。
- **存储**先用单机 SQLite、FTS5 和私有数据目录。原始事件以不可变 JSONL 文件保存，SQLite 保存来源版本、权限、结论、证据引用和复验历史。Markdown 日报从这些记录生成，可重建。备份同时包含数据库和事件文件。
- **后台任务**使用独立 worker，定时总结、补跑和索引更新均由服务执行。开发时可用固定时钟、确定性抽取器和临时数据库，真实实验再启用配置的模型。关闭 Codex 不影响已入库材料的处理。
- **目录分工**建议为 `src/team_memory/{domain,storage,adapters,jobs,api,mcp}`、`tests/{unit,integration,acceptance}` 和 `examples/codex/`。数据库、令牌、真实会话和私有实验报告存放在仓库外。仓库内使用虚构样例。

### 作用域与身份

| 归属 | 典型记录 | 默认读写规则 |
| --- | --- | --- |
| 个人 `personal` | 偏好、更正、在某项目上的个人观察 | 归本人，可带项目标签。项目成员身份不授予读取权。 |
| 项目 `project` | 决策、进度、分工、风险 | 项目成员可读有效结论，有写入权的成员或代理可提交候选，项目授权人可确认。 |
| 群组 `group` | 飞书群内消息和总结 | 归当前群组。群与项目绑定后，只能发布经授权且适合项目成员阅读的提炼结果。 |

“协作”是内容属性，可以通过参与人、提出人、负责人和确认人表达。给私人记录加项目标签或提到某个人，都不会扩大可见范围。跨范围共享时新建一条具有独立可见范围的项目记忆，保留内部来源关联。读者看不到原文时，只返回已授权的项目说明，隐藏原文、标题、路径和受限参与人。

请求身份包含客户端、代表的主体及授权范围，由服务端凭证解析。传入 `project_id` 只能限定本次查询。首轮用三个身份做测试：本人、仅有项目权限的协作者、无关项目成员。搜索、详情、引用、日报和复验列表均走同一权限判断。

## 3. 数据、状态与接口契约

下表给出首版迁移必须支持的逻辑实体。实现时可合并物理表，但要保留唯一性、历史及事务约束。

| 实体 | 关键字段与约束 |
| --- | --- |
| 空间与授权 | `space_id, kind, owner_id`；授权记录包含 `principal_id, space_id, role`。飞书群映射和群到项目的绑定独立保存，可撤销。 |
| 来源版本 | `source_id, adapter, external_id, revision, space_id, author_id, occurred_at, ingested_at, content_hash, blob_ref`。同一来源版本唯一；相同版本但正文不同返回冲突。上游没有版本号时用内容哈希生成版本。 |
| 记忆版本与证据 | `memory_id, version, kind, claim, space_id, subjects, state, effective_at, recorded_at, supersedes`。每条证据绑定来源版本与消息、段落或行号。保存证据质量、判断理由和抽取器版本。 |
| 复验项与决定 | `review_id, candidate_version, prior_version, reason_codes, reviewer_scope, status, decision_by, decision_at, edited_claim`。确认写入操作者、依据及结果。并发复验使用预期版本。 |
| 作业与请求 | 摘要保留空间、当地日期、已处理的来源版本、规则版本和运行状态。写请求以主体、操作、`request_id` 去重，并保存请求摘要及首次结果。 |

写入顺序为先落盘来源文件并校验哈希，再在 SQLite 事务中登记来源及待处理作业。worker 只处理已登记的文件，中断留下的孤立文件可在重试时复用。当索引或 Markdown 尚未重建时，读取端仍检查数据库中的权限、状态和版本；过期的投影跳过或按当前版本重新生成。

**生效规则。** 新结论先生成候选。满足第 4 节规则后进入 `active`，人工驳回则标记 `rejected`。修订先生成新版本，生效时在一个事务内将旧版标记为 `superseded`。撤回后标记 `revoked` 并从当前上下文、索引和派生摘要中移除。若当前版本需要重新核实，单列“有争议”，保留上一确认时间，暂停作为确定事实注入。历史视图区分“何时生效”和“系统何时知道”。复验暂缓保留候选并记录再次提醒时间。

| 能力 | HTTP 契约 | Codex 入口与要点 |
| --- | --- | --- |
| 批量采集 | `POST /v1/sources` | 适配器使用，逐项返回新增、已存在或失败及原因，失败项可有选择地重试。 |
| 提交记忆或纠正 | `POST /v1/memories` | `record_memory` 接收正文、目标空间、证据、请求 ID 和可选被修订版本，返回记忆 ID、状态和复验原因。用户明确陈述保留其消息引用。 |
| 取项目或个人上下文 | `POST /v1/context` | `get_context` 接收空间和长度预算，返回有效结论、日期与可见引用。待确认事项需显式请求，并单独列出。 |
| 检索与核实 | `POST /v1/search`、`GET /v1/memories/{id}` | `search_memory`、`get_memory`。先取得授权候选，再排序。详情支持指定历史版本，返回可见证据及状态。 |
| 处理复验 | `GET /v1/reviews`、`POST /v1/reviews/{id}/decisions` | `list_reviews`、`open_review` 帮用户定位具体条目；决定端点要求人工身份。支持确认、修改后确认、驳回、暂缓。 |

同一请求 ID 和相同内容返回首次结果，复用 ID 提交不同内容返回 `409`。记忆版本已变或复验已被他人完成，同样返回 `409` 并提示刷新。缺少身份返回 `401`。已认证但无权读取具体对象时，与对象不存在统一返回 `404`。

## 4. 定时总结和人工复验

**每日总结。** 默认在空间当地时间 02:00 处理前一日已采集的新增、修订和撤回事件。时区默认 `Asia/Shanghai`，时间和时区均可配置。worker 启动时补齐错过的窗口，也支持按空间、日期手动补跑。个人日报提取偏好、纠正和可复用经验；项目日报提取决定、状态变化、分工、风险与待确认项。每条结论附证据。输入按作用域切分，避免私有材料在生成共享摘要前被拼入提示词。

一次执行固定输入版本清单，按新增来源逐条抽取，用稳定键保存候选。迟到事件或上游编辑会重新打开受影响的日期。模型超时、响应解析失败或进程重启时，失败批次可重试，完整落库后才推进处理进度。重复摘要引用同一条原始消息，只计一份证据。来源删除或绑定撤销时，先取消受影响内容的可见性，再重算摘要和索引。

**复验分流。** 在 CoPaw 已有的风险分类和复验队列上，增加逐条证据判断。模型置信分可用于排序，决策同时考虑原话、来源身份、是否转述、是否冲突和结论影响范围。

| 命中条件 | 处理结果 |
| --- | --- |
| 用户本人明确陈述个人偏好，或可信项目记录中有授权人直接确认，证据可定位且无冲突 | 按所在空间策略生效，保留理由与证据。普通 Agent 的总结只能作为派生证据。 |
| 模型推测、间接转述、缺少原始依据、结论超出引文，或低置信度 | 建立待复验项并指明缺哪项证据。已有旧版时并列展示。 |
| 与有效决定冲突、更改对外承诺、代他人认领职责 | 转交有权确认的人。影响某人分工时，展示本人或有权分派者的依据。 |
| 来源失效、原确认人撤回、到达显式复查日期 | 重新检查受影响的有效记忆。仍有独立证据则重算，证据不足则移入复验。 |

规则按“来源失效 → 冲突或重大承诺 → 证据不足 → 满足生效条件”顺序判定。任何未识别情形均保留为候选。把判定原因及规则版本写入记录，以便以后用人的纠正校准阈值。

**人的操作。** 在 Codex 请求“列出待我确认的记忆”，每项呈现结论、疑点、关键引文和原有效版本。选择条目后打开本机服务的复验页，由用户用独立于 Agent 凭证的个人登录态提交。链接只定位条目，服务端复核权限、版本和人工身份。驳回后，相同来源、版本和结论再次总结时复用驳回决定；出现新依据才重新排队。这样可直接测量复验耗时、改写率和重复打扰次数。

## 5. 开发任务与完成条件

按依赖顺序领取。每个任务完成时提交对应代码、迁移或样例，以及能独立运行的验收测试。下列路径和命令是实现目标。

| 任务 | 依赖 | 代码工作 | 完成条件 |
| --- | --- | --- | --- |
| T1 服务骨架与隔离 | 无 | 建立 `pyproject.toml`、数据库迁移、凭证解析、空间授权、HTTP 健康检查和基础 CLI。使用私有数据目录与测试用临时目录。 | 空目录启动、二次启动、备份还原成功。三种身份通过读写权限矩阵测试。 |
| T2 来源采集与 Codex 导入 | T1 | 定义来源适配器。实现显式清单导入，支持选定的 Codex 会话摘要、个人笔记及项目 Markdown/评审摘录。先输出 dry-run 报告，再按清单导入。允许重复运行同一清单采集文件修订。 | 可查看来源、目标空间、条数、重复、缺失及解析失败。重复导入不增量，摘要标注为派生来源。导入过程只读原文件。 |
| T3 证据、查询与 Codex MCP | T2 | 实现候选/有效版本、查询详情、FTS5、中文短词与项目代号的检索基线、上下文预算和读写 MCP 工具。此阶段新提交统一进入候选，使用固定有效记录测试读取。若检索漏掉同义问法，可用相同题库比较 sqlite-vec 混合检索与基线。 | 新 Codex 会话可查到仅存在于测试服务的唯一事实并引用证据 ID。短中文查询可命中，项目身份无法通过搜索、详情或引用读取个人内容。 |
| T4 定时总结与恢复 | T2、T3 | 实现调度、按范围补跑、抽取器、增量游标、来源版本去重、摘要生成及失效重算。开发测试用固定抽取结果，真实实验走所配置的模型。 | 覆盖跨日、迟到事件、重复运行、模型失败和中途终止。服务重启后补齐任务，两次处理同一输入只形成一份候选。 |
| T5 人工复验与纠正 | T3、T4 | 实现证据规则、复验列表、本机复验页、人工身份、四种决定、版本冲突、替代与撤回传播。 | 第 1 节全流程通过。两人同时确认只有一次成功；相同证据被驳回后不重排；撤回后搜索、上下文和可见日报都更新。 |
| T6 Codex 真实项目实验 | T1–T5 | 选择本人、一个真实项目和经选择的协作记录。建立固定问题、预期答案及证据，对照运行并记录结果。真实材料和报告保存在私有目录。 | 通过第 6 节的 Codex 验收；报告明确列出失败用例与依据。该里程碑可在没有飞书、没有 Friday 的环境独立交付。 |
| T7 CoPaw 迁移与飞书群聊适配 | T1–T5，可与 T6 独立验收 | 建立 CoPaw 个人、群组、项目工作区映射，并核对旧 `memory.db` 的记录和来源。实现 `feishu_group` 适配器，读取选定的飞书群归档 JSONL，按群 ID、消息 ID、发送身份、事件时间和修订归一化。绑定项目时走授权提炼流程。 | 迁移报告给出读取、归并、隔离、失败数量及旧 ID 对照，原库保持只读。用两个群、一个项目验证重复、修订、跨群不可见、授权发布和解绑撤回。 |

T7 定义的首版交付是**飞书群历史归档接入**。实时订阅飞书事件可沿用同一适配器扩展。CoPaw 历史库导入时先核对来源文件和索引条目，路径无法解析的旧记录单列，保留其旧标识，待核实后再进入有效记忆。

### 目标运行方式

以下命令约定用于开发交接和 CI。实现 T1 时固定 CLI 名称与配置，后续任务逐步实现对应子命令。T2 要在 `examples/codex/` 提供清单和可分发的虚构输入。清单中的路径相对清单文件解析。例如，以下条目将评审记录导入项目空间；个人笔记使用独立的个人空间，导入时由操作者分别授权。

```toml
[[sources]]
adapter = "project_document"
external_id = "atlas-release-review"
path = "fixtures/release-review.md"
space = "project:atlas"
```

```sh
uv sync
uv run team-memory init --data-dir ~/.local/share/team-memory-lab
uv run team-memory import --manifest examples/codex/atlas.toml --dry-run
uv run team-memory import --manifest examples/codex/atlas.toml
uv run team-memory digest --space project:atlas --date 2026-11-16
uv run team-memory serve --host 127.0.0.1 --port 8765
```

`init` 将实验数据目录写入当前服务配置。配置中指定模型、时区和授权映射。为简单部署，初版可由 `serve` 同时拉起并监管唯一 worker；也提供独立 worker 入口给部署环境。正常运行不依赖手工调用 `digest`。Codex 测试客户端在另一个终端读取已签发、仅限实验空间的令牌后接入。

```sh
codex mcp add team-memory --url http://127.0.0.1:8765/mcp --bearer-token-env-var TEAM_MEMORY_TOKEN
uv run pytest tests/unit tests/integration tests/acceptance
```

## 6. Codex 实验、证据与发布门槛

先用虚构夹具跑自动测试，再用同一个真实项目跑人工实验。实验开始前固定问题、标准答案、允许使用的来源、预期可见身份。两组使用相同模型、项目快照、原生记忆设置和全新会话，一组启用 team-memory，一组关闭。在两组开始前，用导入器在服务端放入一条带随机标记的测试决定，输入文件位于两组均无权读取的目录。先跑关闭组，再跑启用组，以免启用组的答案进入原生记忆后干扰基线。保存实际 MCP 调用和引用 ID；答对且能定位证据才算有依据的命中。这条随机样例用于验证接入，另外 20 道固定问题用于比较质量。

| 验收项 | 通过条件 |
| --- | --- |
| 检索与项目接手 | 建议首轮固定 20 问，其中 16 问有确定依据，4 问证据不足或仍待复验。建议通过线为至少 14/16 问结论及引用均正确，4/4 问准确标出不确定。私有报告记录两组结果和差值。另在启用组验证唯一测试决定的标记及引用。 |
| 总结正确性 | 正常定时、断点补跑和重复执行产生一致的有效结论。抽查每项摘要均能定位到原始或明确标识的派生证据。 |
| 人工复验 | 测试集中所有低置信、转述分工和冲突用例进入预期队列。四种处置结果正确。记录误送复验数、人工修改数和每项处理耗时，用于调整规则。 |
| 权限与时效 | 未授权披露、待复验事项被当成确定事实、已撤回决定出现在当前上下文，这三项的允许数量均为零。各测一次直接查询及通过日报、引用间接读取。 |
| 飞书群聊 | 使用 T7 的独立样例出具结果。区分“Codex 实验通过”和“飞书群归档适配通过”。 |

第一轮开发从 **T1、T2 和第 1 节样例**开始。完成 T5 后先执行完整的虚构项目验收，再引入真实个人记忆和协作记录。
